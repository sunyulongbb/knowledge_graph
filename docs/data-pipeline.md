# 数据录入与知识清洗原型

## 功能边界

```text
MySQL / CSV、Excel、JSON / Wikidata
  → 读取和预览 → 选择保留列 → 保存二维实体表
  → 实体表输入 → 本体对齐 → 属性对齐 → 实体对齐 → 知识融合 → 知识库输出
  → 全量预览 → 人工确认 → 保存现有知识库
```

录入模块不创建知识、本体或属性。预览运行只保存运行记录，不修改知识实体或属性。正式运行先生成全量待确认计划；点击“确认保存知识库”后才执行写入。

沿用项目现有批量录入和清洗的管理员权限。暂存表、流程、运行记录按当前应用及创建用户隔离；修改已有知识仍检查其所有者或维护授权，管理员身份不能覆盖他人知识的维护权限。

## 页面入口

- **数据录入**：新建录入、实体表。
- **数据清洗**：清洗流程、运行记录。
- Wikidata 的复杂 SELECT 编辑器位于默认折叠的“高级设置”。“打开现有 SPARQL 工具（独立页面）”链接进入 `/sparql?db=当前知识库`，保留原有端点、模板、查询和导入功能。旧 `?tool=sparql#entry` 链接自动跳转，保留知识库参数。原有 SPARQL 接口没有删除或替换。
- 普通录入页面的保存动作只保存实体表。原有录入、批量清理代码和接口保留，新菜单默认进入上述闭环。

## 如何演示完整流程

### 1. 准备本体和属性

登录管理员账号，选择一个用于演示的应用。

在现有本体管理中选择或创建“人物”和“国家”本体，在“人物”下关联以下属性。也可使用已有属性，ID 不需要与下表一致。

| 名称 | 数据类型 | 配置 |
| --- | --- | --- |
| 出生日期 | `time` | 作为生日映射目标 |
| 国籍 | `wikibase-item` | 尾实体本体选择“国家” |
| 职业 | `string` | 演示文本属性融合 |

如使用已有实体引用类型的“职业”，需要配置对应尾实体本体。属性选项实时读取所选本体的已关联属性，包含继承属性。

### 2. 读取并保存实体表

进入“数据录入 → 新建录入”。任选一种来源：

- **数据库**：勾选“使用演示数据”，测试连接、读取字段、读取并预览。界面明确标记为演示，不会假装连接了 MySQL。
- **文件**：下载并选择 [pipeline-people.csv](../public/examples/pipeline-people.csv)。运行中的下载地址是 `/examples/pipeline-people.csv`。也支持 UTF-8 CSV、`.xlsx`、`.xls` 和对象数组 JSON；Excel 可选择工作表后点击“读取文件”。
- **Wikidata**：类型填 `Q5`、语言 `zh`、数量 `10`；可用 `P27` / `Q148` 筛选国籍。网络可用时通过已有 SPARQL 客户端读取；高级查询必须是 SELECT。

文件演示将来源标识改为 `pipeline-demo:people`，名称填“人物原始表”，勾选需要保留的列，点击“保存实体表”。此时知识库不发生变化。

### 3. 配置清洗流程

在“实体表”列表中点击“开始清洗”。默认提供连接好的六步流程，也可以删除节点后从左侧拖回画布：

1. **实体表输入**：选择“人物原始表”，检查字段、记录数和下方预览。
2. **本体对齐**：选择当前应用的“人物”。
3. **属性对齐**：默认自动识别 `id`、名称、别名、描述、标签五类基础字段，可手动调整。将 `birthday`、`country`、`occupation` 映射到上述三个属性。不使用的剩余字段必须显式选择“忽略此字段”。
4. **实体对齐**：查看规则，不需要配置相似度或脚本。
5. **知识融合**：选择“保留原值”“使用新值”或“合并为多值”。空原值总是接受新值，相同值自动去重；名称冲突保留原名称，并把新名称加入别名。
6. **知识库输出**：检查运行和确认说明。

修改流程名称并保存。可拖动节点标题调整位置；点击上游“输出”再点击下游“输入”建立连接。“清空连接”和“按顺序连接”用于重建单向流程。

基础字段单独显示，不需要先关联本体属性：

| 目标字段 | 自动识别列名示例 | 保存与融合 |
| --- | --- | --- |
| 唯一标识 | `id`、`source_id`、`qid`、来源ID | 用作来源实体标识 |
| 名称 | `name`、`label`、`labels`、`itemLabel`、名称 | 写入实体名称；冲突时保留原名称，新名称加入别名 |
| 别名 | `aliases`、`alias`、`aliases_zh`、别名 | 写入实体别名，合并去重 |
| 描述 | `description`、`descriptions`、`desc`、描述 | 空值填入；差异按保留／替换／合并策略处理，合并以换行分隔且去重 |
| 标签 | `tags`、`tag_list`、标签 | 使用项目标签字段，合并去重 |

名称、别名、描述可读取 Wikidata 的多语言对象，如 `{"zh":{"language":"zh","value":"张三"}}`。基础字段语言默认中文，也可选择英文；不存在所选语言时依次尝试语言主码、中文、英文和首个可用值。别名和标签也支持 JSON 数组以及逗号、分号、顿号、竖线、换行分隔的文本。标签是本项目的扩展字段。

自动识别不会覆盖手工清空的基础字段或已保存的自定义属性映射。除唯一标识与名称可以共用一列外，同一列不能同时映射到两个基础字段，或既作基础字段又作自定义属性。取消某个基础字段映射后，原列可在下方改映射到属性或显式忽略。切换本体保留基础字段配置，切换实体表会重新识别。

### 4. 预览、确认并检查知识库

点击“预览运行”，默认最多处理前 100 条，显示每个节点的处理摘要和明细。已有同名同本体实体会成为“疑似对齐”，可选择关联具体候选、创建新实体或跳过。

处理完疑似记录后点击“正式运行（全量预览）”，重新计算全部已读取数据。确认新增、更新、跳过、新增属性、冲突、失败和待确认数量，再点击“确认保存知识库”。有未决疑似记录时不能确认。失败行展示原因并不入库，其他成功行可以确认。

进入知识管理查看结果。国籍保存为现有格式的实体引用，能用于关系展示；缺少对应“国家”实体时会在计划中创建，新增实体数包含这些尾实体。

在“运行记录”中可查看原始数据、映射值、候选、冲突结果及状态；可重新打开待确认的运行。重复确认同一次运行不会重复写入。

### 5. 演示二次融合

下载 [pipeline-people-update.csv](../public/examples/pipeline-people-update.csv)，作为新实体表录入，**来源标识仍填 `pipeline-demo:people`**。复制相同配置方式建立一个新流程：

- `10001`：来源 ID 已知，确定匹配原“张三”；“张三的新名称”加入别名，职业差异按选定策略融合。
- `10002`：来源 ID 与值相同，去重，不重复创建。
- `20003`：“王五”同名同本体但来源 ID 不同，进入人工疑似对齐。
- `10004`：新实体。
- `10005`：日期非法，作为失败行展示，不产生部分知识或尾实体。

处理疑似记录后重新生成全量预览并确认。再次运行时，已保存的来源 ID 可以确定匹配，避免重复建实体。不同数据源应使用不同的来源标识，避免把无关系统的相同 ID 当成同一来源。

## 接口

前缀为 `/api/kb/pipeline/`，沿用 `?db=<当前应用标识>`。请求和响应为 JSON。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `mysql` | `{ action: "test" | "fields" | "read", demo?, connectionName, host, port, database, username, password, table, sql }` |
| POST | `wikidata` | `{ entityType, language, limit, property?, value?, query? }`，读取为二维表 |
| GET / POST | `tables` | 列出 / 保存实体表 |
| GET | `tables/:id` | 表元数据、字段及全部暂存记录 |
| GET / POST | `flows` | 列出 / 保存流程；POST 携带 `id` 时更新自己的流程 |
| GET | `flows/:id` | 恢复节点、位置、配置和连接 |
| GET | `properties?ontologyId=...` | 当前本体已关联及继承的属性 |
| POST | `run` | `{ flowId, mode: "preview" | "full", decisions?: { "行索引": { action: "link" | "new" | "skip", entityId? } } }` |
| POST | `confirm` | `{ runId, confirm: true }`，确认服务端保存的全量计划 |
| GET | `runs` | 最近 100 次运行的摘要 |
| GET | `runs/:id` | 运行结果、行明细和当时的流程快照 |

保存实体表示例：

```json
{
  "name": "人物表",
  "sourceType": "file",
  "sourceKey": "pipeline-demo:people",
  "columns": ["id", "name", "occupation"],
  "rows": [{"id": "10001", "name": "张三", "occupation": "工程师"}]
}
```

`sourceKey` 是来源命名空间；唯一标识字段的值是来源 ID。确定匹配键是“应用 + 来源命名空间 + 来源 ID + 本体”。系统不把外部数据的数字 ID 直接当成本地实体主键。来源关联首次在确认成功后建立。

## SQLite 表及写入行为

第一次访问新接口时幂等创建以下表，仍使用现有应用 SQLite 数据库：

| 表 | 保存内容 |
| --- | --- |
| `entity_tables` | ID、名称、应用、创建者、来源类型、来源标识、记录数和时间 |
| `entity_table_columns` | 字段名称和顺序 |
| `entity_table_rows` | 按行索引保存的 JSON 数据 |
| `cleaning_flows` | 流程名称、应用、创建者和更新时间 |
| `cleaning_flow_nodes` | 六种节点、位置和 JSON 配置 |
| `cleaning_flow_edges` | 节点连接 |
| `cleaning_runs` | 运行方式、状态、流程快照、处理结果和确认计划 |
| `cleaning_entity_sources` | 来源 ID 与本地实体的确定对应关系，用于再次运行去重 |

实体表通过 `PipelineStore` 统一访问，前端不接触 SQL。确认阶段在一个 SQLite 事务中写入现有 `nodes`、`attributes`、来源关联及完成状态。异常时整体回滚，运行仍为待确认，可检查后重试；被判定为失败的原始行不包含在写入计划中。

预览到确认之间若当前应用的知识、本体或属性发生变化，服务端拒绝旧计划，要求重新计算，避免用过时预览覆盖新数据。

数据录入页已删除旧表单、任务编辑器、直接导入逻辑、初始化请求和专用样式，由新流程统一渲染；旧录入任务的后端接口和已保存数据保留。SPARQL 页面独立为 `public/sparql.html`，主页面不再加载其脚本和样式。原有本体、属性、知识展示和 SPARQL 功能继续保留。复用 `BusinessGridController`、现有 XLSX 组件、`loadOntologyProperties`、SPARQL 客户端、Wikidata 值和 statement 规范化、现有知识访问及创建者记录机制；没有引入新前端框架或 ETL 依赖。

MySQL 使用 [Bun 原生 SQL MySQL 适配器](https://bun.sh/docs/runtime/sql)，支持连接测试、字段读取和 SELECT 查询，不新增驱动包。密码只保留在当前表单和请求，不持久化。服务端使用只读会话及 SELECT 子集检查；连接账号应配置为只读账号。

## 验证与原型限制

```powershell
bun run typecheck
bun test
bun run build
node scripts/check-pipeline-browser.mjs
```

浏览器检查使用 Node 22+、现有 Bun 与本机 Chrome/Edge。可通过 `CHROME_PATH` 指定浏览器。浏览器运行在独立临时配置中，测试服务只绑定 `127.0.0.1`，知识数据仅在内存；原型验证不需要使用真实应用账号或生产数据。

- 单表最多 10000 行、200 列；上传文件最多 20 MB，保存的记录 JSON 最多 20 MB。此原型不做流式处理。MySQL 超出行数限制会要求缩小查询范围，不静默丢弃超限记录。
- MySQL 真实连接需提供可达数据库，已验证演示适配器和只读查询校验，未做真实 MySQL 联调。
- Wikidata 使用现有网络客户端和 `WIKIDATA_SPARQL_ENDPOINT` 设置，实时读取依赖外网；已验证查询构建与只读限制，未把模拟响应当作外部服务联调结果。
- 实体匹配仅来源 ID 或同名同本体；没有相似度、AI、自动合并疑似实体。
- 文本引用自动创建尾实体要求属性已配置尾实体本体。同名尾实体不唯一时要求提供明确 ID，不能自动任意选择。
- 现有 `chat.ts`、`core-kb.ts` 的类型检查错误仍存在；新增模块没有新增类型错误。完整验证结果见本次交付说明。
